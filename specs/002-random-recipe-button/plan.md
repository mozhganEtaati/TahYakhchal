# Implementation Plan: Random Recipe Button

**Branch**: `002-random-recipe-button` | **Date**: 2026-09-09 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/002-random-recipe-button/spec.md`

## Summary

One press returns one random Persian dish — title, ingredients, ordered steps — with no photo
and no typed ingredients. Pressing again returns a dish the user has not seen this visit.

Technical approach: a second route handler, `POST /api/random`, that asks the same Gemini
model for a single dish while passing the titles already seen this visit as an exclusion list.
It reuses feature 001's recipe schema, validation, 30-second ceiling, error codes, and
friendly Persian messages wholesale — the only genuinely new pieces are the route, a home
screen control, and a visit-scoped list of seen titles held in the existing session context.

Deliberately a separate endpoint rather than a flag on `/api/suggest`: the request carries no
photos and no ingredient pool, and the floor rule (FR-008, at least 2 recognized ingredients)
must not apply. Bending the existing endpoint to mean two different things would weaken the
contract that Principle IV asks us to keep stable.

## Technical Context

**Language/Version**: TypeScript 5.x on Node.js 20+ — unchanged from feature 001.

**Primary Dependencies**: No new ones. Next.js 15, `@google/genai`, `zod`, Tailwind v4 +
shadcn/ui, `motion`, `lucide-react` are all already in the project.

**Storage**: None added. The seen-this-visit list is React state that dies on reload. A random
dish the user saves rides on the existing FR-013a `localStorage` carve-out with no change.

**Testing**: Manual verification against `quickstart.md`, consistent with feature 001. No
principle or requirement in this spec calls for automated tests.

**Target Platform**: Any standard Node.js-compatible host. Unchanged.

**Performance Goals**: One dish per press, single user. Result or friendly failure inside 30
seconds (FR-106, SC-106) — the same ceiling feature 001 established.

**Constraints**: `GEMINI_API_KEY` stays server-side (FR-016 still binds). All copy Persian and
RTL. The control must not disturb photos or ingredients the user has already entered (FR-110).

**Scale/Scope**: One new route, one new component, one new context field. ~4 files touched.

the new component owns its own result rendering so the home screen stays a composition of
independent parts. `lib/` gains only additive exports — nothing existing changes signature,
which is what keeps feature 001 working untouched while this is built.
